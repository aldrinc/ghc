# Hermes Sidecar Local Prototype Plan

**Date:** 2026-03-31
**Status:** Draft for execution review

## Decision

Start with **Option A locally on purpose**.

The goal of this plan is **not** to prove the final production architecture. The goal is to validate, as quickly as possible, that a Hermes-backed sidecar can deliver the V3 interaction model you actually want:

- a skill-loaded agent
- persistent conversational revision
- explicit draft and approval flow
- usable page/copy outputs
- enough robustness to justify further investment

If this local prototype works well, we can then decide whether to:

- harden Hermes-first further
- keep Hermes only as an adapter
- move the same flow behind an mOS-native control plane later

For now, speed of validation wins.

## Prototype Question

Can we stand up a **local Hermes sidecar** attached to a minimal mOS tool boundary and prove this end-to-end flow:

1. user opens a scoped agent thread
2. Hermes loads the correct profile and projected skill context
3. user chats with the agent
4. agent drafts or revises copy/page outputs
5. mOS stores draft artifacts or draft page versions
6. user approves explicitly
7. mOS promotes the selected output without manual copy/paste

If the answer is yes, the prototype is successful.

## Scope

Build the smallest slice that still proves the interaction model.

In scope:

- one local workspace scope
- one Hermes sidecar instance scope
- one `copy` profile first
- one approved skills context fixture
- one conversational thread type
- one draft -> revise -> approve flow
- one page-aware path after the copy-only path works
- mOS-owned artifact persistence and approval records
- local-only runtime projection generation
- local-only Hermes home lifecycle

Recommended initial subject:

- one presell page rewrite flow

Optional second subject after the first flow works:

- one sales page rewrite flow

Out of scope for the first prototype:

- multi-tenant production hosting
- pooled Hermes workers
- full memory federation
- all 34 skills
- general-purpose agent profiles
- full campaign strategy orchestration
- production deployment
- broad external actuation

## Prototype Principles

1. Error clearly instead of guessing.
   Missing required inputs, missing bundle roles, inconsistent defaults, or blocked approvals should fail with explicit errors.

2. Do not mount the raw `mos_strategy_v3` export directly.
   Use projected runtime files only.

3. Keep mOS canonical for anything the user may later trust.
   Drafts, approvals, selected outputs, and provenance must land in mOS.

4. Keep Hermes state local and disposable.
   The prototype should rely on Hermes session continuity, but not require Hermes to be the only source of truth.

5. One profile, one flow, one happy path first.
   Do not try to prove the whole platform in the first cut.

## Local Prototype Shape

### Runtime boundary

Use this local arrangement:

- `marketi` runs the backend, database, and minimal tool boundary
- Hermes runs as a local sidecar process
- Hermes connects to mOS through a minimal MCP surface
- Hermes home is scoped per local test workspace/profile
- projected skills and overlays are generated into a local runtime directory

### Recommended local scope key

Use one concrete local scope:

- `org_id`
- `client_id`
- `product_id`
- `agent_profile = copy`

### Recommended Hermes home layout

Use a disposable local prototype directory such as:

```text
/Users/aldrinclement/Documents/programming/marketi/.local/hermes/
  org_<org_id>/
    client_<client_id>/
      product_<product_id>/
        copy/
          SOUL.md
          config.yaml
          skills/
          memory/
          sessions/
          state/
```

Rules:

- generated by mOS
- safe to delete and recreate
- never treated as canonical business storage

## Prototype Data Strategy

Use a fixture-driven approach first.

Recommended fixture:

- the EMBER example bundle from `mos_strategy_v3/FutrGroup-Hookd-Project/EMBER/`

Do not start by solving the entire `skills` provider ingestion stack.

Instead:

1. create one local approved bundle fixture representation in mOS
2. generate one runtime projection from that fixture
3. prove the conversational flow against that projected context

That gives you fast signal on the UX and runtime behavior before full ingestion work.

## Minimal Prototype Entities

Add only the minimum mOS records needed to support the local flow cleanly.

Required first:

- `agent_threads`
- `agent_turns`
- `runtime_sessions`
- `approval_items`

Reuse where possible:

- `agent_runs`
- `agent_tool_calls`
- `agent_artifacts`

Add next, once page flow starts:

- `site_page_context_bindings`
- `site_page_agent_sessions`

Do not start with a full generalized memory platform.

For the prototype, memory can be:

- Hermes local memory
- optional mOS memory candidate writes only

## Minimal MCP Tool Surface

Start with a deliberately small toolset.

Read tools:

- `mos.thread.get`
- `mos.thread.history`
- `mos.context.get_active_bundle`
- `mos.page.get_context_binding`
- `mos.memory.search`

Write tools:

- `mos.artifact.save_draft`
- `mos.page.save_draft_version`
- `mos.memory.write_candidate`

Approval/finalization tools:

- `mos.approval.create`
- `mos.artifact.promote`
- `mos.page.promote_version`

Operational tools:

- `mos.job.start`
- `mos.job.status`

Rules:

- all write tools must be typed
- all write tools must log provenance
- high-risk actions remain mOS-mediated
- Hermes should not get unrestricted filesystem or browser power through the prototype tool boundary

## Runtime Projection Model

For the prototype, build one projection generator for the `copy` profile.

Inputs:

- approved skills fixture bundle
- profile definition
- model policy
- local tool manifest
- optional approved memory projection

Outputs:

- generated `SOUL.md`
- generated profile config
- projected skill subset
- runtime overlay files
- tool/MCP registration config

The prototype projection should contain only what the `copy` profile needs.

Do not project:

- unrelated skills
- all repo memory files
- the full raw `~/.claude`-style export

## Conversational Flow To Prove

### Flow 1: Copy-only draft loop

1. user creates a `copy` thread
2. backend creates or resolves a Hermes runtime session for that scope
3. backend generates the runtime projection if missing or stale
4. Hermes loads the projected `copy` profile
5. user asks for a rewrite against the approved context
6. Hermes calls read tools to pull thread history and context
7. Hermes produces a draft
8. Hermes calls `mos.artifact.save_draft`
9. user reviews draft in chat
10. user asks for revisions
11. Hermes revises against the same thread and session
12. user approves
13. Hermes or mOS creates the approval item resolution
14. mOS promotes the selected draft canonically

Success signal:

- no copy/paste bridge is needed
- draft and final are both visible in mOS with provenance

### Flow 2: Page-aware draft loop

Only start after Flow 1 works.

1. user opens or creates a page bound to approved context
2. mOS resolves `site_page_context_binding`
3. user invokes `Use Copy Agent`
4. Hermes loads the same `copy` profile plus page binding snapshot
5. Hermes writes slot assignments or a bounded draft page update
6. mOS persists a new draft `SitePageVersion`
7. user reviews in chat and through page diff
8. user approves
9. mOS promotes the selected page version

Success signal:

- page edits remain bounded
- provenance links the draft back to thread, run, bundle, and page binding

## Phased Build Plan

### Phase 0: Local spike

Goal:

- prove that Hermes can drive one local scoped thread through a minimal mOS MCP surface

Build:

- one local Hermes sidecar runner
- one `copy` profile projection
- one minimal MCP server
- one thread type
- one draft save tool
- one promote tool

Exit criteria:

- user can chat with the Hermes-backed copy agent
- draft -> revise -> approve works for one artifact

### Phase 1: Local platform foundation

Goal:

- make the spike durable enough to evaluate UX and robustness

Build:

- `agent_threads`
- `agent_turns`
- `runtime_sessions`
- `approval_items`
- local Hermes home lifecycle manager
- run/session metadata persistence
- typed tool registry for the minimal toolset

Exit criteria:

- sessions can be resumed
- thread history is durable
- approvals are separate from drafts

### Phase 2: Robust copy-agent prototype

Goal:

- make the `copy` profile feel real, not just technically connected

Build:

- cleaner `copy` runtime projection
- approved bundle fixture loader
- draft artifact versioning
- revision loop in chat
- explicit finalization step
- local run viewer or debug view for tool calls and outputs

Exit criteria:

- copy flow feels conversational and usable
- user can iterate before approval without losing continuity
- errors are clear and reviewable

### Phase 3: Page-aware validation

Goal:

- prove that the same Hermes-backed thread model works for page output, not just abstract copy artifacts

Build:

- `site_page_context_bindings`
- `site_page_agent_sessions`
- bounded page draft write path
- `Use Copy Agent` local entry point
- draft page diff + promotion path

Exit criteria:

- draft page versions can be created and reviewed
- approved versions promote cleanly
- page provenance is inspectable

### Phase 4: Robustness pass

Goal:

- test whether the flow survives normal local failures and interruptions

Validate:

- Hermes process restart
- backend restart
- session resume
- missing required inputs
- invalid or contradictory bundle state
- interrupted run followed by user revision
- stale runtime projection regeneration

Exit criteria:

- failures are diagnosable
- retries are predictable
- no hidden runtime mutation becomes required for correctness

## Validation Scenarios

Run these scenarios before calling the prototype successful.

### Scenario 1: Happy-path copy refinement

- start a new copy thread
- ask for a rewrite
- review draft
- request one revision
- approve final draft

### Scenario 2: Hard rejection

- reject the first draft
- ask for a different direction
- confirm the second draft is a distinct version, not an overwrite

### Scenario 3: Session continuity

- close Hermes
- restart Hermes
- continue the same thread
- verify Hermes session continuity plus mOS draft continuity

### Scenario 4: Missing required inputs

- remove a required bundle role or experiment spec
- confirm the system errors clearly
- confirm no synthetic fallback is silently injected

### Scenario 5: Page-bound flow

- bind a page to approved context
- run the copy agent
- persist a draft page version
- approve the promoted page version

### Scenario 6: Scope isolation

- create a second local scope
- confirm Hermes home, memory, and session continuity do not bleed across scopes

## Exit Criteria

Do not call the prototype validated until all of these are true:

1. A Hermes-backed `copy` thread works end-to-end in local chat.
2. The agent can revise work conversationally before approval.
3. mOS stores draft and final outputs canonically.
4. Approval is explicit and separate from generation.
5. The projected runtime profile is enough; the raw `mos_strategy_v3` export is not mounted directly.
6. Session restart and resume are understandable.
7. Missing required inputs fail clearly.
8. The page-aware flow works for at least one bounded page path.
9. Provenance is visible across thread, run, tools, and output version.

## What We Explicitly Defer

Defer these until after the prototype proves the flow:

- multi-profile rollout beyond `copy`
- generalized skill registry UI
- full memory approval platform
- broad cross-agent memory sharing
- large tool surfaces
- multi-user concurrency
- pooled Hermes workers
- production deployment
- mOS-native runtime adapter implementation

## Immediate Build Order

Do these first, in order:

1. Pick the exact local fixture bundle and the one prototype page flow.
2. Add the minimum thread/session/approval records.
3. Stand up the minimum MCP server and tool registry.
4. Generate one scoped `copy` Hermes projection locally.
5. Prove draft -> revise -> approve for a copy artifact.
6. Add the page binding and draft page version path.
7. Run the restart, rejection, and missing-input scenarios.

## Recommendation

If the goal is to get to a live-feeling V3 interaction quickly, this is the right first move.

But the prototype must stay disciplined:

- small scope
- local only
- one profile first
- explicit approvals
- no silent repair behavior
- no pretending the raw export is already a production runtime package

That gives you the fastest path to real UX validation without locking the long-term architecture before you have evidence.
