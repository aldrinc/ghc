# Site Import Screenshot-to-Code Adapter Plan

## Decision

Rip out the current MOS-native site import path and replace it with a `screenshot-to-code` driven import flow.

The new boundary is:

1. `screenshot-to-code` is the import engine.
2. `screenshot-to-code` generates `react_tailwind` output.
3. MOS no longer tries to interpret reference sites on its own.
4. MOS import logic is rewritten into an adapter that converts generated React/Tailwind into Marketi-native Puck templates and variant data.
5. MOS organizes imported pages under a higher-level site object so related pages stay grouped as one site.
6. `Site` is a separate runtime object, not a `Funnel` subtype or alias.
7. MOS reuses the existing `screenshot-to-code` generation surface instead of inventing a more complex MOS-specific route unless a real blocker appears.

This is the intended simplification:

- no MOS heuristic section detection
- no MOS-local import normalization pipeline as the source of truth
- no HTML import path
- React + Tailwind only

## Explicit Model Policy

This thread explicitly authorizes the import model order.

The import system should use exactly these two model slots:

1. Gemini
2. Claude Opus

Rules:

- No automatic model discovery from whichever API keys happen to be present.
- No model cycling beyond these two explicit slots.
- No third fallback model.
- If only one import candidate is generated by default, use Gemini.
- If two import candidates are generated, slot 1 is Gemini and slot 2 is Claude Opus.
- If Gemini fails and the flow is configured to attempt the second explicit slot, Claude Opus is the only allowed second attempt.

Exact model IDs should be frozen in config, not inferred dynamically at runtime.

## Upstream Retention Policy

MOS should retain the full upstream output from `screenshot-to-code` by default.

That means:

- do not reduce the response down to only parsed Marketi fields
- do not discard upstream events or metadata without explicit approval
- persist the raw upstream output alongside the adapted Marketi data

The import pipeline should therefore have two parallel outputs:

1. raw upstream `screenshot-to-code` output
2. adapted Marketi/Puck output

The raw upstream output is the source record.
The adapted output is the MOS interpretation layer.

## What Changes

### Remove from MOS

The following MOS behavior should be removed from the production import path:

- heuristic import normalization
- heuristic section candidate extraction as the primary interpretation layer
- MOS deciding template structure from raw source HTML
- MOS acting like its own screenshot-to-code system

Practically, the current production path centered around these files should be retired or rewritten:

- `mos/backend/app/services/site_import_normalize.py`
- `mos/backend/app/services/site_imports.py`
- `mos/backend/app/services/site_import_capture.py` for anything beyond screenshot acquisition
- `mos/backend/app/services/template_synthesis.py` as the first interpretation step for imported sites

### Keep in MOS

MOS should still own:

- import job records
- screenshot acquisition from a source URL, if we still need URL import entry
- storage of source screenshots and provenance
- adapter output persistence
- review UI
- draft variant creation
- governance and publish approval

### Add to MOS

MOS needs a new adapter layer that consumes generated React/Tailwind and emits Marketi-native structures:

- normalized sections
- theme candidate
- synthesized Puck data and template-mapped draft payloads
- provenance tying the draft back to the source URL, screenshots, model, and generated code
- site-level grouping for related pages

## Target Architecture

### Ownership

| System | Responsibility |
| --- | --- |
| `screenshot-to-code` | Generate React/Tailwind from screenshots using the approved model slots |
| MOS | Persist import jobs, call the generator, adapt React/Tailwind into Puck-backed Marketi data, organize related pages into sites, present review, create draft variants |

### Target flow

1. Operator submits a site import in MOS.
2. MOS creates a site-level import object that will own one or more related pages.
3. MOS captures the desktop/mobile screenshots needed for each page in the import set.
4. MOS sends those screenshots or videos to the existing `screenshot-to-code` generation surface.
5. MOS defaults generation settings to:
   - `generatedCodeConfig = react_tailwind`
   - model slot 1 = Gemini
   - model slot 2 = Claude Opus
6. `screenshot-to-code` returns its existing output stream and completion data for each page.
7. MOS stores the full upstream output.
8. MOS adapter parses the generated React/Tailwind output.
9. MOS adapter classifies each page by site family and page role.
10. MOS adapter maps each page into the relevant Puck template and Marketi-native data.
11. MOS stores the page set under one site object with inter-page links and page-role metadata.
12. Reviewer inspects the adapted result in the existing Store Templates flow.
13. MOS persists draft variants and the usual governance process continues.

The important boundary is:

- source site -> page screenshots/videos -> `screenshot-to-code`
- generated React/Tailwind -> MOS adapter -> Puck template mapping -> Marketi site + page variants

## Site Object Model

MOS needs a first-class site object above individual imported pages.

The current codebase already has the right starting point in:

- `mos/backend/app/services/site_blueprints.py`

That file defines:

- `SiteFamilyDescriptor`
- `SitePageBlueprint`

For example, `medusa-b2b-starter` already describes a related page set:

- `home`
- `category`
- `product_detail`
- `cart`
- `checkout`

The new import flow should land on that level of abstraction, not just isolated page variants.

There is already site-family/page-blueprint logic in the current backend, plus a current `/sites` surface:

- `mos/backend/app/services/site_blueprints.py`
- `mos/backend/app/routers/sites.py`
- `mos/backend/app/schemas/sites.py`

But the current runtime implementation treats a site as a funnel-backed experience.
That is not the target architecture.

This plan should instead introduce a dedicated site runtime model.

### Required concepts

The import system should represent:

- one imported site
- one site family
- many imported pages
- page roles within the site
- links between pages
- an entry page

Suggested runtime model:

- `Site`
- `SitePage`
- `SitePageVersion`
- `SiteLink` or equivalent link metadata

Suggested import-side model:

- `ImportedSite`
- `ImportedSitePage`
- `ImportedSiteEdge` or equivalent link metadata

### Minimum site-level fields

For the site object:

- site import id
- site family
- site type
- commerce provider
- source hostname
- entry page type
- imported page count
- completeness state

For each page:

- page type
- template id
- source URL
- source screenshot refs
- generated React/Tailwind code
- adapted Puck data
- outbound links to other page types

### B2B starter requirement

For `medusa-b2b-starter`, the adapter should understand that these are pages within one site:

- homepage
- category page
- product detail page
- cart page
- checkout page

Those should not be treated as unrelated page imports.

They should be stored and reviewed as one site family instance with linked page records.

## Core Design Decisions

### 1. React + Tailwind is the only import output we support

Use `react_tailwind` as the canonical import output.

Do not support:

- `html_tailwind`
- raw HTML/CSS
- Vue
- Bootstrap
- mixed import stacks

Why:

- one import shape is easier to parse, validate, and govern
- JSX trees are a better adapter target than raw HTML snapshots when the goal is Marketi-native component mapping
- Tailwind classes expose layout and style intent cleanly enough for token extraction

The existing `screenshot-to-code` request surface already supports:

- screenshots via `inputMode = image` and `prompt.images[]`
- videos via `inputMode = video` and `prompt.videos[]`

MOS should use those existing modes directly.

### 2. Rewrite MOS import logic into the adapter

The MOS import system should stop trying to be an analyzer.

Its job becomes:

- request generated React/Tailwind
- parse JSX and Tailwind
- map that structure into the correct Puck templates, sections, and blocks
- persist the result

This means the old import logic should be treated as scaffolding to replace, not preserve.

### 3. The generator remains upstream of Marketi

`screenshot-to-code` output is not the final runtime template.

It is the upstream reference artifact that MOS adapts into:

- variant draft data
- style preset data
- reviewable section coverage
- provenance metadata

We still should not persist imported reference code as the production storefront runtime.

### 4. Reuse the existing generation surface with MOS defaults

MOS should start by reusing the existing `screenshot-to-code` `/generate-code` surface rather than creating a bigger custom contract.

That means MOS should send the existing request shape with defaults such as:

- `generatedCodeConfig = react_tailwind`
- `inputMode = image | video`
- `prompt.images[]` or `prompt.videos[]`
- approved model slot defaults

MOS should consume the existing output stream and store it in full.

If later we find a concrete integration blocker, we can add a thinner backend wrapper, but that should not be the default design assumption now.

### 5. The adapter must terminate in real Puck templates

The adapter is not done when it produces generic normalized sections.

It is only done when it can map the imported page into a concrete Puck-backed target.

That means:

- select the correct site family
- select the correct page blueprint
- select the correct base Puck template
- map adapted sections into that template's supported block vocabulary
- produce reviewable synthesized Puck data

For the existing B2B site family, this should align with real templates already in the repo:

- `medusa-b2b-home`
- `medusa-b2b-category`
- `medusa-b2b-pdp`
- `medusa-b2b-cart`
- `medusa-b2b-checkout`

The import pipeline should explicitly target those templates, not stop at generic page summaries.

### 6. The operator flow must include import UI, Puck review UI, and save UI

The plan is incomplete unless it covers:

- how the import is started
- how import progress is shown
- how imported pages are reviewed
- how Puck-mapped output is inspected before save
- how the reviewed site/pages are committed into the saved site model

This needs to be treated as part of the core scope, not a later polish item.

## Adapter Design

### Adapter input

The adapter should take:

- source URL
- source screenshots or videos
- generated React/Tailwind code
- generation metadata
- raw upstream `screenshot-to-code` event transcript
- requested page type hint, if present

### Adapter output

The adapter should produce:

- `themeCandidate`
- `normalizedSections`
- `suggestedTemplateFamily`
- `siteFamily`
- `pageType`
- `templateId`
- `synthesizedPuckData`
- draft-ready Puck-backed structure
- import provenance
- site-level organization metadata
- reference to the raw upstream `screenshot-to-code` payload set
- save-ready site/page/version payloads aligned with the dedicated Site runtime

Suggested provenance fields:

- source URL
- source hostname
- screenshot capture timestamp
- generator system = `screenshot-to-code`
- stack = `react_tailwind`
- model slot used
- exact model ID
- generated code hash
- input mode used
- raw upstream transcript/storage key

### Site family classification

Classify the imported page into a site family before template mapping.

For example:

- `medusa-b2b-starter`

This classification should be grounded in the existing site family registry in `site_blueprints.py`.

### Page role classification

Classify each generated page into the relevant page role within that family:

- `home`
- `category`
- `product_detail`
- `cart`
- `checkout`

### JSX parsing

Parse the generated React component tree and identify:

- page shell
- top-level sections
- nested content groups
- CTA components
- media components
- repeated proof/review structures

### Tailwind extraction

Use Tailwind classes to infer:

- spacing rhythm
- typography scale
- color usage
- layout density
- border and radius language
- CTA treatment

### Puck template selection

Use the site family and page role to resolve the correct base template.

For `medusa-b2b-starter`, that should use the existing blueprints and template ids in `site_blueprints.py`.

### Puck block mapping

Map adapted structures into the existing Puck/Marketi concepts:

- hero
- proof bar
- feature stack
- comparison
- review/testimonial wall
- FAQ
- footer
- other template-family-specific sections

### Site graph extraction

Extract inter-page relationships from the generated output and source page context:

- header nav links
- CTA target intent
- cart and checkout transitions
- breadcrumb or collection-to-product transitions

Those relationships should be stored at the site-object layer.

### Variant payload generation

From the adapted structures, build:

- accepted sections for reviewer inspection
- style preset candidates
- variant provenance
- synthesized Puck data for draft creation
- site-level page linkage metadata
- page-level draft payloads for `SitePageVersion`

## What The Adapter Should Not Do

- It should not guess from source HTML when generated React/Tailwind is available.
- It should not fall back to the old MOS heuristics silently.
- It should not rewrite the generated code and then use that rewritten code as the source of truth.
- It should not choose a different model than the explicit slot policy.
- It should not stop before the page is mapped to a concrete Puck template.
- It should not treat related site pages as unrelated standalone imports.
- It should not discard upstream output fields without explicit approval.

## screenshot-to-code Changes Required

### 1. Keep the existing generation surface as the primary integration point

The route does not need to become more complicated than it already is.

Primary recommendation:

- use the existing `/generate-code` surface
- use the existing request shape
- set MOS defaults on the MOS side

That keeps the integration small and preserves compatibility with what `screenshot-to-code` already knows how to do.

### 2. Remove dynamic model selection from the MOS path

Current `screenshot-to-code` behavior includes provider-driven model selection and model sets.

That is not acceptable for MOS import.

The MOS import path should:

- bypass `ModelSelectionStage`
- bypass model sets derived from available keys
- reject requests without the explicit approved model configuration

### 3. Preserve the full existing output surface

MOS should capture and store everything `screenshot-to-code` currently emits, including the structured event stream.

That includes current websocket message types such as:

- `status`
- `setCode`
- `variantComplete`
- `variantError`
- `variantCount`
- `variantModels`
- `thinking`
- `assistant`
- `toolStart`
- `toolResult`

If `validated_loop` is used, MOS should also retain the validated-loop metadata and artifacts when returned.

### 4. Support both screenshots and videos

MOS import must support both existing input modes that `screenshot-to-code` supports:

- screenshot/image imports
- video imports

The integration should use the existing payload fields:

- `prompt.images[]`
- `prompt.videos[]`

### 5. Keep the defaults simple

MOS should default:

- stack to `react_tailwind`
- model slot 1 to Gemini
- model slot 2 to Claude Opus

Those defaults should be applied by MOS when constructing the existing request payload.

### 6. Support the two explicit model slots

Recommended config in `screenshot-to-code` for MOS import:

- `MOS_IMPORT_MODEL_SLOT_1`
- `MOS_IMPORT_MODEL_SLOT_2`

Initial values should map to:

- slot 1: Gemini
- slot 2: Claude Opus

MOS can either request:

- a single slot
- or both slots for a two-candidate import review flow

## MOS Changes Required

### 1. Replace current import orchestration

The current import orchestration should be rewritten around:

- screenshot acquisition
- generator invocation
- adapter execution
- persistence

The old path of capture -> heuristic normalize -> synthesize should be removed from production use.

The replacement path should end in save-ready site/page/version records for the new Site runtime, not just review-only import artifacts.

### 2. Introduce a dedicated adapter service

Add a new MOS service layer, for example:

- `site_import_adapter.py`
- `site_import_generator_client.py`

Responsibilities:

- call `screenshot-to-code`
- consume the existing websocket event stream
- persist the full upstream payload set
- parse returned React/Tailwind
- generate Puck-template-mapped Marketi-native data
- attach pages to a site-level object
- return a save-ready site/page/version result

### 3. Keep import jobs async

Even with the simpler architecture, imports should run asynchronously.

Recommended statuses:

- `queued`
- `capturing`
- `generating`
- `adapting`
- `completed`
- `failed`

### 4. Persist generated code explicitly

Persist the upstream generated code and metadata explicitly.

Do not bury it in an unstructured JSON blob only.

Recommended persisted fields:

- generated React/Tailwind code
- generated code hash
- model slot
- exact model ID
- generator metadata
- raw upstream event transcript
- raw upstream event payloads
- tool event payloads
- status event payloads
- thinking / assistant event payloads
- variant completion/error payloads
- resolved site family
- resolved page type
- resolved template id
- target site id, page id, and draft version id once saved

### 5. Persist raw upstream output as a first-class record

MOS should explicitly persist the full `screenshot-to-code` output set.

At minimum, that means storing:

- the original generation request sent to `screenshot-to-code`
- the full ordered websocket transcript
- final code payloads
- returned model metadata
- validated-loop result payloads when present
- artifact paths / run dirs when present
- errors exactly as returned

The adapted Marketi output should be stored separately from this raw upstream record.

### 6. Add site-level persistence

MOS should persist a site-level object that groups imported pages.

This should align with the existing site family/page blueprint model.

At minimum, persistence needs to represent:

- one imported site record
- one or more imported site page records
- page ordering
- entry page
- page-to-page linkage
- page-to-template mapping

### 7. Introduce a dedicated Site runtime

The import save path should target a dedicated site runtime model rather than the current funnel-backed site abstraction.

Recommended runtime objects:

- `Site`
- `SitePage`
- `SitePageVersion`
- `SiteLink` or equivalent site-graph representation

That means the save path should create or update:

- the site record
- the page set
- page ordering and entry page
- internal page links
- draft `puck_data` for each page version

The current funnel-backed `/sites` implementation can be used as a reference for API shape and blueprint application, but it should not remain the persistence boundary for imported sites.

### 8. Reuse the review UI where possible

The current Store Templates review surface can remain if its data source changes from heuristic imports to adapter output.

That means the frontend can still review:

- site family and imported page set
- screenshots
- upstream generator transcript / metadata
- normalized sections
- suggested family
- target Puck template
- theme candidate
- draft conversion result

But the backend source of those values changes completely.

## UI Requirements

The user interface has to cover four distinct operator moments:

1. start import
2. monitor generation/adaptation
3. review site and page mappings
4. save reviewed output into the system

### 1. Import entry UI

Location:

- current `Store Templates` area is the most obvious starting point
- primary file today: `mos/frontend/src/pages/workspaces/StoreTemplatesPage.tsx`

Required inputs:

- source URL
- import mode:
  - screenshot/image
  - video
- optional site family hint
- optional page-type or page-role hint
- workspace/product context

Defaulted and not manually required unless we later expose advanced settings:

- stack = `react_tailwind`
- model slot 1 = Gemini
- model slot 2 = Claude Opus

Required operator feedback:

- what will be imported
- what defaults are being applied
- whether the run will create one page or a multi-page site import

### 2. Import progress UI

The operator needs a progress surface that shows more than a single status string.

Required states:

- queued
- capturing
- generating
- adapting
- ready for review
- failed

Required progress detail:

- current page being processed
- input mode used
- active model slot
- whether raw upstream output has been captured

Required error behavior:

- show the exact upstream error returned by `screenshot-to-code`
- show the exact adapter/save error returned by MOS
- do not collapse failures into a generic "import failed"

### 3. Site-level review UI

Before the operator reviews page details, they need a site-level overview.

Required site-level review sections:

- detected site family
- entry page
- imported page set
- page roles
- inter-page linkage
- completeness state

For `medusa-b2b-starter`, the review UI should make it obvious that the operator is reviewing:

- home
- category
- product detail
- cart
- checkout

as one site, not five unrelated drafts.

### 4. Page-level review UI

For each imported page, the operator should see:

- source screenshot or video reference
- raw generated React/Tailwind availability
- target page type
- target template id
- mapped sections
- theme candidate
- Puck mapping summary

The page-level review must answer:

- what page role did MOS assign?
- what Puck template will this save into?
- what content/sections were mapped?
- what is still missing or blocked?

### 5. Puck review UI

The operator needs a real Puck-level inspection step before save.

Required minimum review affordances:

- show that synthesized `puckData` exists
- show the target template id
- show structure/governance validation
- show the page rendered through the existing Puck runtime if possible

Preferred implementation path:

- reuse the existing Puck editor and render patterns already used in
  `mos/frontend/src/pages/research/funnels/FunnelPageEditorPage.tsx`

This is a UI/runtime rendering reference only, not a persistence-model dependency.

That means import review should not stop at JSON inspection only.

It should support an operator seeing the actual Puck-rendered page state before committing it into the saved site.

### 6. Save UI

The operator needs a clear save action with a clear save target.

Required save actions:

- save reviewed import into a target site
- create a new site record when the operator chooses a new-site save
- save page drafts into that target site
- optionally re-run adaptation before save if the review state changed

Required save feedback:

- site created or updated
- page count saved
- entry page assigned
- draft version ids created
- any page that failed to save

The save CTA should not be ambiguous.
It should tell the operator that MOS is saving a site and page drafts, not just a temporary import artifact.

### 7. Post-save navigation

After save, the operator should land somewhere useful.

Recommended destination:

- the saved site detail view if we expose a site management page
- or the existing page editor flow for the entry page/site pages

Minimum post-save actions:

- open saved site
- open page editor
- return to import review

## Save Flow Requirements

The save flow must explicitly cover how adapted Puck output becomes stored runtime data.

### Save target

Use a dedicated site persistence model:

- `Site` for the site record
- `SitePage` for each page
- `SitePageVersion` for each saved draft
- `SiteLink` or equivalent relationship metadata for inter-page navigation

### Save steps

1. Create or resolve the target site record.
2. Create or resolve the page set from the selected site family blueprint.
3. Attach page roles and ordering.
4. Save adapted `puck_data` into draft page versions.
5. Rewrite internal links so page-to-page navigation uses real saved page ids.
6. Persist provenance that links saved records back to the import and raw upstream output.

### Save behavior questions the implementation must answer

- Are we always creating a new site, or can we save into an existing site record?
- Can the operator save only a subset of imported pages?
- What happens if one page saves and another fails?
- Do we create all page drafts in one atomic transaction or per-page with recovery?

These questions should be answered before implementation, not left implicit.

## Main Risks

### Risk 1: The adapter from JSX to Marketi blocks is harder than expected

This is the real technical risk now.

Mitigation:

- keep a single import stack
- parse JSX structurally instead of string-munging
- keep the first adapter focused on current supported families only
- require concrete Puck-template resolution, not generic page summaries

### Risk 2: The model contract drifts back into auto-selection

Mitigation:

- explicit slot config only
- MOS import path bypasses dynamic model selection
- tests assert exact slot usage

### Risk 3: We keep too much of the old import path around

Mitigation:

- define the old path as removed from production scope
- quarantine or delete heuristic normalization once the adapter path is validated

### Risk 4: Review quality regresses if we skip adaptation rigor

Mitigation:

- persist generated code for debugging
- persist the full upstream event/output transcript for debugging
- expose provenance in review
- validate adapted section quality on a real comparison set before full cutover

### Risk 5: The UI stops at review and does not actually close the save loop

Mitigation:

- scope save UX now, not after backend work
- target the dedicated site/page/version persistence model
- include post-save navigation in the implementation scope

## Candidate Discards Requiring Explicit Approval

Do not discard any of these now.

If you later want to reduce storage, these are the first candidates I would bring back for your approval:

- repetitive `status` messages if they provide no durable value beyond the ordered transcript
- duplicate `setCode` payloads when the final stored code is byte-identical
- ephemeral `eventId` values if they are only transport identifiers and not used for replay/debugging
- local `artifactPath` / `runDir` values if they are sidecar-local and not stable across environments
- verbose `thinking` / `assistant` traces if you later decide they are too expensive to retain long-term
- `toolStart` / `toolResult` payload bodies if they become too large and prove low-value in practice

Again: these are suggestions only.
The current plan is to retain them all unless you approve otherwise.

## Acceptance Criteria
